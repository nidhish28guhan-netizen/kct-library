SIMPLE LIST OF SOFTWARE ENGINEERING & AGILE CONCEPTS ACTUALLY USED IN THIS PROJECT
Course 24CSI015 · College Library Management System (CLMS) v1.0
One line per concept: what it is, and exactly where we used it in this project.

=====================================================================
UNIT I — FUNDAMENTALS & DESIGN
=====================================================================
- Process model choice          — compared Waterfall/Spiral/Agile, picked incremental Agile (docs/unit-1 §1)
- Vision statement              — one-paragraph system purpose (blueprint §1, unit-1 §2.1)
- Stakeholder analysis          — Student/Faculty/Librarian/Admin mapped to real screens (unit-1 §2.2)
- Functional requirements (FR)  — 17 "the system shall" items, each traced to code (unit-1 §2.3)
- Non-functional requirements   — security/reliability/usability/performance/maintainability with evidence (unit-1 §2.4)
- SRS                           — the requirements pack assembled from the blueprint (§§1–16) in unit-1
- Use-case diagram              — actors + main goals, drawn in Mermaid (unit-1 §5.1)
- Class diagram                 — Member/Book/BookCopy/Loan/Reservation/Penalty/Policy etc. (unit-1 §5.2)
- Sequence diagram              — issue and return call flows, step by step (unit-1 §5.3–5.4)
- State machine                 — copy lifecycle AVAILABLE/ISSUED/RESERVED/LOST/DAMAGED/MAINTENANCE (unit-1 §4.4)
- ER diagram / data model       — entities and relationships of the library (unit-1 §4.1–4.2)
- Layered architecture          — routes → services → domain → repositories → store (unit-1 §3.1)
- Modular design                — 12 modules mapped to specific files (unit-1 §3.2)
- Separation of concerns        — pure business rules kept in domain/ with no I/O
- Design decision record        — JSON files instead of PostgreSQL, why and what it costs (unit-1 §4.3)
- Atomic write                  — save to temp file then rename, so data never half-writes (db/store.js)
- Unique identifier design      — barcode built from book code + copy number, LIB-<BOOKCODE>-NNN (unit-1 §6)
- Traceability matrix           — FR → module → test, in unit-1 §2.3

=====================================================================
UNIT II — AGILE PRACTICES & PROJECT MANAGEMENT
=====================================================================
- Agile iteration               — software delivered working every 2 weeks, 7 times
- Scrum roles                   — one dev is Product Owner, the other Scrum Master (unit-2 §2)
- Sprint planning               — story selection per sprint with points (docs/sprint-plan.md)
- Daily stand-up                — 15-min sync, written on the JIRA card
- Sprint review                 — walkthrough of the increment against acceptance criteria
- Retrospective                 — kept/changed note; e.g. S3 retro booked fixer time for S4
- Product backlog               — 10 epics, 37 stories, 126 points (unit-2 §4)
- User story format             — "As a … I want … so that …" for every story
- Acceptance criteria           — Given/When/Then per story, 5 examples in unit-2 §3.1
- Story points                  — relative effort, never hours (unit-2 §4.1)
- Planning poker                — team estimated together, Fibonacci scale 1/2/3/5/8/13
- Velocity                      — completed points per sprint: 17,16,18,22,13,16,23 (mean 17.9)
- Burndown                      — release remaining 126→1 after S7; per-sprint notes in sprint-plan.md
- Carry-over                    — 2 honest carries: US-15 (S3→S4), US-30 (S6→S7)
- Deferral decision             — US-37 (1 pt stretch) moved to v1.1 by the Product Owner, stated openly
- Kanban board + WIP limit      — JIRA columns To Do→In Progress→Code Review→Testing→Done, max 2–3 tasks active
- Lean (waste removal)          — scan-first desk replaces manual entry; MVP freeze stopped scope creep
- XP practices                  — test-first coding, pairing on circulation, small commits, CI on every push
- JIRA as evidence layer        — project CLMS (id 10034), board 35, 55 issues, sprints named on the board
- Workload split                — Nidhish 61 pts / Kawaskar 64 pts across the 7 sprints (sprint-plan §3.3)
- WBS                           — work broken into 3 levels of deliverables (unit-2 §8.1)
- Gantt chart                   — the seven sprint dates drawn for the release (unit-2 §8.2, sprint-plan §4)
- PERT / three-point estimate   — O/M/P per activity, critical path backend→barcode→circulation→testing→ops
- COCOMO II                     — organic model on 1.498 KLOC → 3.67 person-months, 3.86 months schedule
- Function point (count)        — ~230 FP derived from the real files/endpoints, as a size cross-check
- Risk register                 — 6 risks with likelihood×impact and a response each (unit-2 §9)
- Version control / SCM         — Git on main, module-scoped conventional commits (unit-2 §10)
- Baseline                      — release tree + per-milestone commits as restore points
- Project closure               — release 4 Sep 2026 with defect log closed and E2E green

=====================================================================
UNIT III — TESTING, QUALITY & DEVOPS
=====================================================================
- Test pyramid                  — 69 unit / 52 API integration / 2 E2E journeys (121 tests, 6 suites)
- Unit testing                  — Jest on pure domain rules (loan, penalty, queue, barcode, scoring)
- Integration testing           — supertest driving the real 45-route API incl. auth and RBAC
- End-to-end testing            — Selenium headless Chrome, student journey + librarian journey
- Test plan / strategy          — what gets tested at which level and when (unit-3 §1–2)
- TDD red-green-refactor        — the due-date boundary test written first, told step by step (unit-3 §4)
- Regression test               — RES-001 fix pinned by a permanent integration test
- Equivalence partitioning      — valid/invalid classes for limits, dues, copy states, search terms (unit-3 §3.1)
- Boundary value analysis       — 13/14/15-day, dues 49/50/51, renews 1/2/3, hold 48 h, queue 5 (unit-3 §3.2)
- Decision table testing        — issue-eligibility and renewability rules as tables (unit-3 §3.3)
- Coverage measurement          — Istanbul: 82.04 % stmts / 88.13 % lines overall (unit-3 §7)
- Coverage rule / gate          — three core modules ≥ 80 % (domain 96.83, repositories 97.05, routes 85.41); CI fails below bar
- Cyclomatic complexity (McCabe)— avg 2.13, max 14, four hotspots >10 listed and test-pinned (unit-3 §6)
- Halstead metrics              — per-file effort computed from the AST (docs/metrics-report.json)
- Static analysis               — tools/analyze.js over acorn ASTs, regenerable with npm run metrics
- Defect lifecycle              — NEW→ASSIGNED→IN PROGRESS→FIXED→RETEST→CLOSED (§33 flow)
- Defect log / bug report       — RES-001, UI-002, E2E-003 with full repro/expected/actual/fix/close fields (unit-3 §9)
- Severity vs priority          — Major/High on RES-001 and UI-002; Minor/Medium on the flaky E2E selector
- Escaped-defect tracking       — zero product defects found after release week
- ISO/IEC 25010                 — all 8 quality characteristics assessed with evidence (unit-3 §10)
- CMMI (level 3 practices)      — mapping of process areas to our ceremonies/tests/metrics (unit-3 §14)
- CI pipeline                   — GitHub Actions: install, test+coverage gate, metrics, frontend build (unit-3 §11)
- Build automation              — npm scripts: seed/test/coverage/metrics/build; vite build for SPA
- Containerisation              — backend alpine image + healthcheck; frontend multi-stage build into nginx
- Docker Compose                — backend + web services, named data volume, start-order by health
- Deployment design             — same-origin single port (Express serves dist) and container topology
- Software maintenance types    — corrective (3 defects), adaptive (policies as data), perfective (search/rec tuning, US-37),
                                  preventive (coverage+complexity ratchets) — all with real examples (unit-3 §12)
